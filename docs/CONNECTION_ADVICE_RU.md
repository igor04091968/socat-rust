# Пассивная диагностика соединений

Режим `recommend` собирает статистику реальных подключений и раз в заданный
период пишет `connection_advice` в обычный журнал relay. Он не создаёт проверочных
соединений, не отправляет тестовые сообщения и не меняет параметры сокетов,
конфигурацию или требования TLS/ГОСТ. Это первый этап настройки по наблюдениям;
автоматическое применение рекомендаций пока не реализовано.

Добавьте таблицу к нужному профилю в relays.toml:

```toml
[relay.advice]
mode = "recommend"             # "off" по умолчанию
period_seconds = 900            # период сводки: 1..86400 с
min_samples = 20                # 1..512 успешных TCP-подключений за окно
timeout_min_seconds = 3        # нижняя граница рекомендации
timeout_max_seconds = 30       # верхняя граница, не более 120 с
```

Границы должны удовлетворять `1 <= min <= max <= 120`. Это границы совета,
а не изменение действующего `connect_timeout_seconds`. Профиль перезапускается
обычным способом после изменения конфига. Старые конфиги работают без изменений.
Режим доступен в современных TCP/TLS/ГОСТ-сборках; `legacy-kernel` отклоняет
его при проверке конфига. Windows 7 этим изменением не поддерживается.

## Что означает сводка

- `tcp_ok`, `tcp_errors`, `tcp_timeouts`: завершённые попытки подключения к upstream.
  Неудачные попытки не включаются в задержки успешных подключений.
- `tcp_p95_ms`: p95 времени установки TCP, а не RTT пакета или время банковской операции.
- `tls_ok`, `tls_errors`, `tls_p95_ms`: отдельные измерения исходящего TLS/ГОСТ
  handshake; входящий handshake в эти поля не входит.
- `sessions_ok`, `sessions_errors`: результат обработчика завершённых сессий.
  Это не подтверждение доставки или исполнения транзакции; EOF grace и успешное
  завершение копирования также не являются таким подтверждением.
- `suggested_timeout_seconds`: рекомендация TCP connect timeout или `None`,
  когда данных недостаточно либо есть основания не выдавать совет.
- `degraded`: минимум min_samples завершённых TCP- или TLS-попыток, из которых
  не менее 20% ошибочны. Это пороговая индикация, не диагностика причины.
- `applied=false`: программа ничего автоматически не применила.

В каждом окне хранятся последние 512 успешных TCP и 512 TLS измерений.
Счётчики охватывают все завершённые события окна; память ограничена и не растёт
с числом сессий. На границе окна данные сбрасываются, незавершённая попытка
учитывается в том окне, где завершилась. По умолчанию первая сводка через 15 минут;
после перезапуска история начинается заново. Файла состояния и HTTP-порта нет.
Проверьте, что фильтр журнала разрешает уровень INFO.

Формула совета: округлённое вверх до секунд `4 × TCP p95 + 1 секунда`,
ограниченное указанными min/max. Это эвристика с запасом, не доказанный оптимум.
При недостатке успешных TCP-измерений, любом TCP timeout за окно или `degraded=true`
совет не выдаётся: успешные быстрые подключения могут скрывать медленные отказы.
Редкое длительное соединение может не набрать выборку за окно — это нормально.

Сводка не содержит payload, ключей или сертификатов. Существующие обычные логи
соединений сохраняют своё поведение. Keepalive, буфер, повторные подключения,
таймаут TLS и параметры криптографии здесь автоматически не подбираются.
Активные пробы требуют отдельного согласованного тестового endpoint и в этот
этап не входят.

## Проверка

`scripts/test_advice_integration.py` проверяет пассивность, периодические сводки,
передачу данных при занятом лимите соединений, режим off, ошибки подключения,
а с `--tls` — mTLS и отказ при неверном SAN. Используются только временные
loopback-порты и синтетические сертификаты. Пример для собранного бинарника:

```bash
python3 scripts/test_advice_integration.py \
  --binary artifacts/socat-rust-tls-gost-static --tls \
  --results artifacts/advice-results.json
```
