# Диагностика соединений и автоматический TCP timeout

Режим `recommend` собирает статистику реальных подключений и раз в заданный
период пишет `connection_advice` в обычный журнал relay. Он не создаёт проверочных
соединений, не отправляет тестовые сообщения и не меняет параметры сокетов,
конфигурацию или требования TLS/ГОСТ. Отдельный режим `auto` разрешает ограниченное
изменение таймаута следующих TCP-попыток по этим наблюдениям.

Добавьте таблицу к нужному профилю в relays.toml:

```toml
[relay.advice]
mode = "recommend"             # "off" по умолчанию; "auto" для автоматики
period_seconds = 900            # период сводки: 1..86400 с
min_samples = 20                # 1..512 успешных TCP-подключений за окно
timeout_min_seconds = 3        # нижняя граница рекомендации
timeout_max_seconds = 30       # верхняя граница, не более 120 с
```

Границы должны удовлетворять `1 <= min <= max <= 120`. В режиме recommend
это границы совета, без изменения действующего `connect_timeout_seconds`. Профиль перезапускается
обычным способом после изменения конфига. Старые конфиги работают без изменений.
Режим доступен в современных TCP/TLS/ГОСТ-сборках; `legacy-kernel` отклоняет
режимы recommend/auto при проверке конфига. Windows 7 этим изменением не поддерживается.

## Что означает сводка

- `tcp_ok`, `tcp_errors`, `tcp_timeouts`: завершённые попытки подключения к upstream.
  Неудачные попытки не включаются в задержки успешных подключений.
- `tcp_p95_ms`: p95 времени установки TCP, а не RTT пакета или время банковской операции.
- `tls_ok`, `tls_errors`, `tls_p95_ms`: отдельные измерения исходящего TLS/ГОСТ
  handshake; входящий handshake в эти поля не входит.
- `sessions_ok`, `sessions_errors`: результат обработчика завершённых сессий.
  Это не подтверждение доставки или исполнения транзакции; EOF grace и успешное
  завершение копирования также не являются таким подтверждением.
- `suggested_timeout_seconds`: рекомендация TCP connect timeout или `None`,
  когда данных недостаточно либо есть основания не выдавать совет.
- `degraded`: минимум min_samples завершённых TCP- или TLS-попыток, из которых
  не менее 20% ошибочны. Это пороговая индикация, не диагностика причины.
- `applied`: менялся ли действующий TCP timeout в этой сводке; в recommend всегда false.
- `effective_timeout_seconds`, `previous_timeout_seconds`: новое и предыдущее значения.
- `action`: observe/collect/apply/hold/rollback/cooldown/insufficient_data/mixed_or_errors/degraded.
- `policy_generation`: номер версии таймаута; mixed_generation — завершились попытки
  от разных версий, такое окно не используется для очередного изменения.

В каждом окне хранятся последние 512 успешных TCP и 512 TLS измерений.
Счётчики охватывают все завершённые события окна; память ограничена и не растёт
с числом сессий. На границе окна данные сбрасываются, незавершённая попытка
учитывается в том окне, где завершилась. По умолчанию первая сводка через 15 минут;
после перезапуска история начинается заново. Файла состояния и HTTP-порта нет.
Проверьте, что фильтр журнала разрешает уровень INFO.

Формула совета: округлённое вверх до секунд `4 × TCP p95 + 1 секунда`,
ограниченное указанными min/max. Это эвристика с запасом, не доказанный оптимум.
При недостатке успешных TCP-измерений, любом TCP timeout за окно или `degraded=true`
совет не выдаётся: успешные быстрые подключения могут скрывать медленные отказы.
Редкое длительное соединение может не набрать выборку за окно — это нормально.

Сводка не содержит payload, ключей или сертификатов. Существующие обычные логи
соединений сохраняют своё поведение. Keepalive, буфер, паузы повторных подключений,
таймаут TLS и параметры криптографии здесь автоматически не подбираются.
Активные пробы требуют отдельного согласованного тестового endpoint и в этот
этап не входят.

## Проверка

`scripts/test_advice_integration.py` проверяет пассивность, периодические сводки,
передачу данных при занятом лимите соединений, режим off, ошибки подключения,
а с `--tls` — mTLS и отказ при неверном SAN. Используются только временные
loopback-порты и синтетические сертификаты. Пример для собранного бинарника:

```bash
python3 scripts/test_advice_integration.py \
  --binary artifacts/socat-rust-tls-gost-static --tls \
  --results artifacts/advice-results.json
```

## Включение автоматического применения

Полный пример одного профиля (адрес назначения заменить своим):

```toml
[[relay]]
name = "auto-example"
listen = "127.0.0.1:15000"
upstream = "127.0.0.1:16000"
connect_timeout_seconds = 10

[relay.advice]
mode = "auto"
period_seconds = 900
min_samples = 20
timeout_min_seconds = 3
timeout_max_seconds = 30
stable_windows = 3
cooldown_windows = 3
max_step_seconds = 2
```

- `stable_windows`: 1..24 последовательных окон, каждое с достаточной TCP-выборкой
  и без TCP/TLS/обработанных сессионных ошибок. По умолчанию три окна, то есть
  минимум 45 минут при периоде 900 секунд. Пустое окно прерывает накопление.
- `max_step_seconds`: 1..120, максимум изменения за одно решение в любую сторону.
  По умолчанию два: например, 10 → 8 секунд, а не сразу 10 → 3.
- `cooldown_windows`: 1..96, число периодов без настройки после ухудшения;
  по умолчанию три. После паузы снова нужны stable_windows чистых окон.

На очередной сводке любой TCP timeout актуальной версии либо не менее 20% ошибок
TCP или исходящего TLS при min_samples завершённых попыток актуальной версии
возвращают исходный connect_timeout_seconds и запускают паузу. Программа не
устанавливает причину ошибки: откат выполняется консервативно, даже если проблема
была на сервере или в сертификате. Откат может превышать max_step_seconds,
чтобы сразу вернуть исходное значение. Исходный timeout в auto обязан находиться
в min/max; значение 0 трактуется как штатные 10 секунд и тоже проверяется.

Каждая TCP-попытка получает неизменяемый снимок таймаута. Уже начатую попытку,
установленную TCP-сессию или TLS handshake изменение не прерывает. Следующая
повторная попытка тоже берёт актуальное значение. Поздние результаты старой
версии попадают в сводку, но не вызывают ложный откат и не разрешают очередное
изменение; ошибки актуальной версии учитываются для отката отдельно.

Конфиг на диске не переписывается; после перезапуска снова используется исходное
значение. Для отключения авто-применения выберите `recommend` (сохранить сводки)
или `off` и перезапустите профиль. Динамической перезагрузки здесь нет.
TLS/ГОСТ, CA, проверка имени и клиентские сертификаты задаются как прежде:
автоматика не меняет криптографию, не включает fallback и не посылает проб.
Это настройка времени установки TCP, а не оптимизация банковской транзакции
или гарантия доставки.

Дополнительная проверка: `scripts/test_auto_integration.py` (те же --binary,
--results и опциональный --tls). Она проверяет применение на новых попытках,
сохранение активной сессии, откат при остановке loopback-сервера, восстановление,
проверку границ и сохранение mTLS/отказ при неверном SAN. Неудачные таймауты и
смешанные версии дополнительно проверяются детерминированными Rust-тестами.

Для проверки авто-применения со всеми четырьмя ГОСТ-наборами передайте также
`--gost-fixture artifacts/gost-fixture` в test_auto_integration.py с all-feature
бинарником. Все сертификаты остаются синтетическими.
